# Atomic order intake and replay recovery

The service flushes the new order before it queues scalar-FK dependents, but keeps that flush in the same transaction as the items, history, idempotency record, and outbox event. A request that loses either unique-key race rolls back before it reads durable state, resolving matching submissions as replays and mismatches as the documented `409` conflicts without publishing partial work. The fingerprint now removes SKU-line ordering from request identity while retaining the original `order_time` offset, which M1 stores and uses for local-time fraud decisions. The supplied live PostgreSQL UAT covers normal creation, concurrency, and reordered-item replay.

## High-level view

The parent-first flush establishes the `orders` row before records that reference it only through scalar foreign keys are queued. It does not make the parent visible as an accepted order: one later commit still governs the complete aggregate and its fraud handoff.

Recovery gives a durable idempotency key precedence after rollback. If no key record exists, sales-rep/client-order uniqueness permits an equivalent request to attach its retry key to the committed order; a changed payload remains a conflict.

Sorting SKU lines makes item order non-semantic for both idempotency-key and client-order recovery. The client timezone offset remains semantic because fraud evaluation reconstructs local order time from it.

## Parent-first flush retains all-or-nothing intake

`create_order` flushes the `Order` before it queues `OrderItem`, `OrderStatusHistory`, `IdempotencyRecord`, and `OutboxEvent` with their scalar order references. This avoids relying on ORM relationship ordering for the foreign-key dependents while retaining a single transaction boundary.

```text
request transaction
  Order INSERT + flush             (not committed)
       |
       +-- items, history, idempotency record, outbox event
                                      |
                                      +-- one COMMIT
```

A later child or outbox failure rolls back the flushed parent with the rest of the unit. A concurrent loser of the sales-rep/client-order constraint therefore recovers only after PostgreSQL has resolved the competing transaction, not from a half-written aggregate.

## Unique-key recovery reconstructs the durable winner

After a parent-flush or final-commit `IntegrityError`, recovery rolls back before querying either uniqueness boundary. A matching durable idempotency record replays its order, while a fingerprint mismatch returns `IDEMPOTENCY_KEY_REUSED`. Without that record, an equivalent sales-rep/client-order match receives the new retry key in its own atomic commit; a differing fingerprint returns `CLIENT_ORDER_ID_CONFLICT`.

The second recovery pass handles two equivalent requests attaching the same previously absent key to an already committed order. One idempotency-record insert commits; the other rolls back, reads that record, and returns the same replay without creating another order or outbox event.

## SKU-sorted fingerprints preserve logical replay identity

`_request_fingerprint` uses stable JSON object keys and sorts `items` by `product_sku` before hashing. Duplicate SKUs are rejected, item position is not persisted, and detail reads are SKU-sorted, so reordered SKU/quantity pairs now compare as the same logical request through both recovery paths.

The fingerprint intentionally retains `order_time`'s original offset. The service persists that offset separately, and the fraud evaluator reconstructs client-local time from it; two requests with different offsets can therefore have different M1 fraud outcomes even when their UTC instants match.
