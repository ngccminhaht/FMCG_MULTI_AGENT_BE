# Contract-validated durable order acceptance for the M1 mobile client

The mobile client now treats a create response as completion only when it is an exact `202` with the documented accepted-order shape. It validates the accepted order’s identifiers, timestamps, status, and optional fraud-assessment structure, then requires its `client_order_id` to equal the request stored in the retry queue. Both the immediate submit and bulk-retry paths perform that guarded call before deleting a queue entry. The earlier P1 protections remain intact: durable queue mutations are serialized, competing submit/retry actions are blocked, and pending-fraud polling survives an initial retryable detail failure but stops on terminal outcomes. Watch for: no remaining release-blocking, P1, or P2 behavioral defect was identified in the reviewed paths.

**Verdict**: APPROVED

## High-level view

The accepted `202` is the durability boundary for an order submission. `createOrder` rejects any other success status, malformed accepted body, or mismatched client order ID as incomplete; because those failures retain status `202`, neither submission path classifies them as terminal or removes the persisted request.

The retry queue has two layers of coordination: its AsyncStorage read-modify-write operations run through one promise chain, while the screen keeps submit and bulk retry mutually exclusive. This preserves the persisted payload and idempotency key across network uncertainty without permitting an in-app lost update.

Detail polling remains tied to the currently selected order and its latest status. A known pending order continues toward a retry after a first retryable detail read failure, while a terminal status or terminal detail error disables further scheduling and stale callbacks cannot restart it.

## Accepted 202 responses now guard retry-queue deletion

`FE/src/api/orders.ts:153-181` validates UUID order IDs, known statuses, RFC 3339 timestamps, nullable-or-valid fraud assessments, bounded integer risk scores, and non-empty assessment metadata before returning an exact-`202` response. It then compares the returned `client_order_id` with the request passed into `createOrder` and throws `UNMATCHED_ACCEPTED_ORDER` on a cross-wired response.

That check occurs before either cleanup boundary: immediate submission calls `createOrder(submission.request, submission.idempotencyKey)` before removal in `FE/src/features/orders/M1OrdersScreen.tsx:342-350`, and bulk retry does the same at `:422-425`. An invalid or mismatched accepted response remains a non-terminal `202` failure, so the durable body and idempotency key stay available for a safe retry rather than being discarded.

## Queue serialization and pending-status polling retain their P1 protections

`FE/src/storage/pendingOrders.ts:21-48` serializes every queue read and mutation, including reserve, load, save, and remove. `M1OrdersScreen` adds a synchronous `queueOperationInFlight` gate around submission and bulk retry, so the screen cannot interleave a reserve/remove sequence with a retry pass.

The detail lifecycle at `FE/src/features/orders/M1OrdersScreen.tsx:153-273` keeps a pending target live across retryable failures, applies capped backoff, and cancels the timer whenever selection, status, or screen changes. A refreshed terminal status clears the pending target; terminal detail errors set `pollingStopped`; request generations and the selected-order reference prevent an old response from changing the active detail view.
