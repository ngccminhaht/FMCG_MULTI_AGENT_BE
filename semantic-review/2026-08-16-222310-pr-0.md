# Durable order retries and status polling for the M1 mobile client

The untracked Expo client persists submissions before network calls, serializes retry-queue mutations, and polls the selected order for an asynchronous fraud decision. The earlier P1s are refuted: no two in-app queue read-modify-write operations overlap, and polling ends when the detail reaches a terminal state or receives a terminal error; a retryable first-detail failure retains the known-pending target. Create/list/detail use the OpenAPI’s exact `202`/`200` successes, and the HTTP boundary applies a 15-second abort timeout. **P2, confirmed:** a loosely validated `202` can delete a queued request without proving that the response belongs to that request; the repaired asynchronous behavior also has no automated regression coverage. Watch for: **P2, confirmed** accepted-response correlation before queue cleanup and **P2, confirmed** missing coverage for queue/poll lifecycle regressions.

**Verdict**: NEEDS_CHANGES

## High-level view

The storage promise chain in `pendingOrders.ts` and the screen-level synchronous lock close the earlier lost-update window across submit and bulk retry. Polling is now driven by the latest selected status, is bounded to 3–30-second retries, and starts even when the first detail read of a known-pending order fails.

**P2, confirmed:** `createOrder` only proves that key response fields are non-empty, then both submission paths remove the durable record. The response must be correlated with the saved `client_order_id` and meet the contract’s core identifier, timestamp, and reason-code constraints before it crosses that durability boundary.

**P2, confirmed:** no test harness exercises the serialized storage queue, exact-status/timeout behavior, or detail-poll lifecycle. A type-check cannot catch a new ordering or timer regression in these paths.

## Accepted responses do not establish submission identity

**P2, confirmed:** `FE/src/api/orders.ts:58-95` accepts a `fraud_assessment.reason_codes` array with zero entries and treats `order_id`, `client_order_id`, `created_at`, and `updated_at` as arbitrary non-empty strings. `BE/docs/openapi.yaml:340-399` requires a non-empty reason-code array, UUID order ID, and date-time fields. More importantly, the validator has no relationship to the request, so a valid-looking `202` for a different `client_order_id` passes.

That check controls deletion of the durable submission in both `FE/src/features/orders/M1OrdersScreen.tsx:342-349` and `:423-425`. A cross-wired or malformed accepted response can therefore discard the original retry body and key before the client has established which order was accepted. Require UUID/RFC 3339 values and non-empty reason codes in the response guard, then compare `result.order.client_order_id` with `submission.request.client_order_id`; retain the queue entry and surface an invalid-success error when either check fails.

## The repaired asynchronous paths are untested

**P2, confirmed:** `FE/package.json:6-11` defines no test command, and the complete untracked FE file list contains no tests. Not tested: concurrent reserve/remove operations in `FE/src/storage/pendingOrders.ts:20-165`, a timed-out create followed by same-key replay, terminal-state cancellation of `FE/src/features/orders/M1OrdersScreen.tsx:232-273` polling, and retry after its first known-pending detail read fails. Add deterministic AsyncStorage and fetch mocks for those cases.
