# Durable order intake with concurrent replay recovery

The change flushes an order root before queuing its scalar-FK dependents, then publishes the order, items, status history, idempotency record, and outbox event in one PostgreSQL commit. A request that loses either unique-key race rolls back and reconstructs its outcome from durable idempotency or client-order state, preserving the `202` replay and `409` conflict branches. PostgreSQL unique-index waiting prevents recovery from seeing a competing order until that aggregate transaction has committed; a rolled-back competitor instead leaves the original insert free to succeed. The remaining P2 is that the request fingerprint treats the `items` array as ordered even though the order model and read response treat its SKU lines as unordered.

Watch for: **confirmed (P2)** — a retry whose only change is item-array ordering is rejected as `IDEMPOTENCY_KEY_REUSED` or `CLIENT_ORDER_ID_CONFLICT`, rather than replaying the same logical order.

**Verdict**: NEEDS_CHANGES

## High-level view

The explicit root flush establishes the `orders` row before `order_items`, status history, idempotency, and outbox rows that refer to it only through scalar foreign keys. Because the flush remains inside the request transaction, external sessions receive either the complete aggregate and event or none of it.

Recovery gives the idempotency key precedence over the client-order identifier. A matching durable key replays its order; otherwise a matching client order can acquire the new retry key atomically, while the two documented conflict types remain distinct.

The fingerprint canonicalizes object-key order but retains array order. The persistence model has no item position and detail reads sort by SKU, so ordering should not determine idempotency equivalence.

## Parent-first flush protects the scalar-FK aggregate

`create_order` flushes the new `Order` before it queues `OrderItem`, `OrderStatusHistory`, `IdempotencyRecord`, and `OutboxEvent`. The migration uses immediate foreign keys from each of those records to `orders`, while only `OrderItem` has an ORM relationship that could establish ordering implicitly. The explicit flush makes every child insert valid without depending on relationship configuration.

```text
request transaction
  Order INSERT + flush             (not committed)
       |
       +-- items, history, idempotency record, outbox event
                                      |
                                      +-- one COMMIT
```

The root row remains uncommitted after the flush, so PostgreSQL does not expose it to the worker or another API session without its children and outbox event. If a subsequent insert fails, recovery rolls the entire transaction back; without a competing order it reports an internal failure rather than an accepted order. A competing insert on `(sales_rep_id, client_order_id)` waits for the other transaction to commit or roll back, so a unique-key loser cannot recover against a half-written aggregate.

## Unique-key recovery preserves conflict precedence

On a failed parent flush or final commit, recovery rolls back before looking up state. A durable record for the same idempotency key is authoritative: matching fingerprints replay the original `order_id`, while a different fingerprint produces `IDEMPOTENCY_KEY_REUSED`. When no such key exists, recovery looks up the sales-rep/client-order pair; a different fingerprint produces `CLIENT_ORDER_ID_CONFLICT`, and a matching order receives the new retry key in a separate atomic commit.

The second attempt covers the follow-on race where two equivalent requests both attach the same previously absent retry key to an already committed order. One commit wins, and the other rolls back before reading that winning record on its next iteration.

## Item-list ordering changes idempotency semantics

**confirmed (P2).** `_request_fingerprint` serializes `order_data.model_dump(mode="json")` with sorted object keys, but it does not sort `items`. A first submission with `[SKU-A, SKU-B]` and a retry with `[SKU-B, SKU-A]` therefore produce different stored and incoming fingerprints.

```text
same sales rep, client_order_id, and SKU/quantity pairs

[A, B] --fingerprint--> H1 --first submission--> accepted order
[B, A] --fingerprint--> H2 --same key-------> IDEMPOTENCY_KEY_REUSED
                            --new key-------> CLIENT_ORDER_ID_CONFLICT
```

The database allows one row per SKU and stores no line position, while `get_order_detail` explicitly sorts item lines by SKU. The two payloads consequently denote the same durable aggregate but are classified as different requests, contradicting the contract's equivalent-payload replay and same-client-order semantics. Canonicalize `items` by `product_sku` when constructing the fingerprint, without changing the submitted payload, so both recovery paths compare the same logical order.
