# Strict accepted-response validation and detail recovery

The browser now establishes the accepted-order contract before either submission path deletes its persisted request body and idempotency key. `isRfc3339DateTime` rejects impossible calendar days, out-of-range clock fields, and invalid numeric offsets; accepted-response validation permits risk score `0`, requires a final assessment decision matching a final order status, and verifies UUID-shaped order IDs. `listOrders` and `getOrder` accept only `200`, while `createOrder` accepts only `202`, so a malformed or mismatched accepted response retains the durable retry entry. Pending-detail recovery and malformed-route handling remain intact. **Watch for:** No concrete blocker remains in the requested scope.

**Verdict**: APPROVED

## High-level view

Response validation is the durability boundary: the POST result must satisfy the full accepted-order guard and correlate to the queued `client_order_id` before either normal submission or queue retry removes its entry. Exact expected-status checks keep unexpected successful statuses on the retry path.

Detail state carries a known pending status from list/create navigation and treats an unknown direct link as potentially pending until its first result. A retryable initial read therefore starts bounded polling, while invalid percent encoding resolves to a recoverable list route.

## Accepted-order validation remains ahead of queue cleanup

Both submission paths call `removePendingOrderSubmission` only after `createOrder` returns. The POST must be `202`, satisfy the accepted-order guard, and match the persisted `client_order_id`; any other `2xx`, invalid RFC 3339 value, invalid UUID, non-final or mismatched fraud assessment, or score outside `0` through `100` throws instead and preserves the original body/key pair.

## Initial detail failures still have a recovery path

The route transition retains a known `PENDING_FRAUD_CHECK` status. On a retryable first failure, pending state enables the capped polling loop; the unloaded detail screen also supplies manual retry. `decodeOrderId` catches failed percent decoding before the route is used, so malformed path segments cannot take down rendering.
