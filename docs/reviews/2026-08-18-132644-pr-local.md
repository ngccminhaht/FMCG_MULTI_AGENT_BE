# Durable browser retry and detail recovery

The browser fixes strengthen the order-retry boundary and recover pending details after a failed initial read. They also add manual recovery for an unloaded detail and defensive route decoding. The Web Locks fallback remains scoped to the documented local demo. **Watch for:** **confirmed** the RFC 3339 guard still accepts calendar-invalid timestamps that `Date.parse` normalizes, allowing a malformed `202` to cross the durable queue-cleanup boundary.

**Verdict**: NEEDS_CHANGES

## High-level view

Queue cleanup now follows an exact `202` response guard that accepts zero-valued risk scores, limits fraud decisions to final states, verifies UUIDs and pagination bounds, and correlates the returned client order ID before either submission path removes its saved body/key. **Confirmed**—the shared timestamp check is not strict RFC 3339 validation because JavaScript normalizes impossible calendar values rather than rejecting them.

Known pending status travels from list/create navigation into detail state, while an unknown direct link is treated as potentially pending until its first response. A retryable first failure therefore arms capped polling, and an unloaded detail supplies a manual retry control.

Malformed route segments are rejected before percent decoding can throw; the Web Locks fallback remains confined by the runbook to local-demo scope.

## RFC 3339 validation can normalize invalid calendar dates

**Confirmed.** `apps/web/src/api/orders.ts` accepts a timestamp when it matches a shape regex and `Date.parse` returns a finite value. In the V8 runtime used by the web toolchain, both `2026-02-30T12:00:00Z` and `2026-04-31T12:00:00Z` satisfy those checks because `Date.parse` normalizes them into March and May. Neither is a valid RFC 3339 date-time.

The helper guards `created_at` and `updated_at` on `OrderAcceptedResponse`; `createOrder` returns only after that guard succeeds, and normal submit or queue retry then remove the persisted submission. An API response with an impossible timestamp can consequently be treated as a valid `202` even though the promised success contract was not met.

```text
saved request + Idempotency-Key
            |
POST -> malformed 202 with 2026-02-30 timestamp
            |
shape regex + Date.parse normalization -> accepted response -> queue removal
```

Replace the parse-only semantic check with RFC 3339 validation that rejects invalid month/day combinations and out-of-range time components before any accepted response is returned to `App`.
