# Browser order intake with durable retries

The change adds a Vite browser client for creating, retrying, listing, and polling M1 orders, persisting the original request body and UUID idempotency key before a `POST`. Its default `/api` transport is same-origin through Vite, while the runbook correctly reserves direct CORS and static-host routing for separately configured deployments. **Confirmed**—the web port regresses the earlier success-response guard and initial pending-detail recovery. **Watch for:** **confirmed** valid `risk_score: 0` responses are rejected while malformed accepted responses can cross the queue-cleanup boundary; **confirmed** one transient first detail read strands a pending order without polling or a retry action; **confirmed** a malformed percent-encoded deep link can crash the SPA.

**Verdict**: NEEDS_CHANGES

## High-level view

A submission is reserved in `localStorage` before it is sent, and successful or retryable paths retain the same body/key pair. **Likely**—on browsers without Web Locks, the fallback promise chain serializes only one tab, so two tabs can still race a `localStorage` read-modify-write; the documentation identifies this as a pre-production multi-tab boundary rather than a cross-tab guarantee.

The web client still correlates an accepted response to the saved `client_order_id`. **Confirmed**—the surrounding response checks are weaker than the OpenAPI contract, so they no longer reliably establish that a `202` is safe to use as the durability boundary.

The polling loop has capped 3–30 second backoff, timer cleanup, and stale-response guards once a pending detail has loaded. **Confirmed**—navigation retains only an order ID, not its known pending status, so the loop is never armed when the first detail request fails transiently; the empty state also offers no retry.

The local transport and browser-routing constraints are explicit: Vite proxies `/api`, Vite serves SPA history fallback in development, and the documentation requires a same-origin reverse proxy or reviewed CORS allowlist plus static-host fallback in deployment. **Confirmed security constraint**—the bundled default bearer token and `VITE_*` configuration are suitable only for the documented local demo, not a production browser deployment.

1. **Accepted-order contract guard regressed — confirmed (P2).** Restore strict UUID, RFC 3339, status/decision, risk-score, reason-code, pagination, and exact-success-status validation before a `202` response can delete a persisted submission.
2. **Initial pending-detail failure cannot recover — confirmed (P2).** Carry the list/create response's known pending status into detail navigation or schedule a bounded retry after a retryable initial read, and expose a Retry action when no detail has loaded.
3. **Malformed deep link crashes route parsing — confirmed (P2).** Catch invalid percent decoding in the `/orders/{id}` parser and route it to a recoverable invalid-route/detail state instead of rendering nothing.
4. **Web Locks fallback is not cross-tab durable — likely (scope-bound).** Before presenting the client as a multi-tab workflow, require Web Locks or add a cross-tab coordination strategy that cannot lose a `localStorage` update.
5. **Queue and polling regressions have no executable coverage — confirmed (P2).** Add browser tests for accepted-response validation, same-key replay after timeout, initial-detail retry/backoff, route decoding, and the supported/unsupported Web Locks paths.

<summary>Details</summary>

## Accepted-order validation no longer protects durable cleanup

**Confirmed.** `apps/web/src/api/orders.ts` rejects `risk_score: 0` through `isPositiveSafeInteger`, although the OpenAPI contract permits the inclusive range 0–100. The same guard accepts scores above 100, permits `PENDING_FRAUD_CHECK` as a fraud decision, permits an empty `reason_codes` array, treats any nonempty order ID as valid, and accepts any `Date.parse`-able timestamp rather than the contract's UUID and RFC 3339 values. `listOrders` and `getOrder` also omit their exact documented `200` success status, while list pagination accepts zero or negative metadata.

**Confirmed consequence.** `createOrder` retains the useful `client_order_id` correlation before `App` removes the saved entry, but a replay with a valid final assessment score of zero is treated as incomplete forever. A malformed-but-loosely-shaped `202` can instead be accepted and remove the only persisted retry body/key. The earlier reviewed mobile implementation had strict checks for these fields; the browser port reintroduces that resolved concern.

```text
saved body + idempotency key
        |
POST -> 202 response -> loose response guard -> queue removal
                         ^
                         must enforce the published response contract
```

Restore the prior strict guard, including a terminal `FraudDecision` type, bounds of 0–100, nonempty reason codes, UUID/RFC 3339 checks, valid pagination ranges, and exact `200` expectations for both reads. Retain the current `client_order_id` comparison as the final correlation check.

## First detail failure abandons a known pending order

**Confirmed.** Opening an order from the list and navigating after a successful create both pass only `orderId` into the route. The detail-route effect resets `pollingTargetIsPending` to `false` before its first `getOrder`; that flag is set only after a successful response. A network, timeout, or `5xx` on that first read is retryable, but the polling effect exits because no pending target is recorded.

```text
known PENDING order -> detail route resets pending=false -> first GET fails
                                                     |
                                                     +-> no timer; empty detail shows Back only
```

**Confirmed recovery gap.** The prior client carried list/create status into its detail transition so a first retryable read could enter capped backoff. Preserve that status in route/detail state, or explicitly retry non-terminal initial reads, and add a Retry control to `OrderDetail`'s no-order state.

## Invalid percent escapes take down browser navigation

**Confirmed.** `routeFromLocation` calls `decodeURIComponent` directly on every `/orders/{segment}` pathname. A URL such as `/orders/%` matches the route expression but throws `URIError` during parsing, before the component can render an error state. The SPA fallback can serve `index.html`, but it cannot recover a render-time route-parser exception.

Decode defensively and treat an invalid segment as an invalid detail route or list route.

## Local queue ownership is bounded by browser lock support

**Likely, documented scope constraint.** `pendingOrders.ts` uses Web Locks when available, which coordinates same-origin tabs, but its fallback is an in-memory promise chain that exists only within one document. Two tabs in a browser without Web Locks can concurrently read and overwrite the same `localStorage` array; idempotency protects the server from duplicate accepted orders, but it cannot restore a locally lost pending entry.

The runbook explicitly leaves multi-tab policy, browser storage, and session/token handling for pre-production resolution. That scope makes the limitation non-blocking for the stated local/demo boundary, but it needs a capability gate or real cross-tab coordination before broader browser use.

## Vite proxy and deployment boundary remain local-only

**Confirmed security/deployment constraint.** The Vite configuration proxies `/api` and `/health` to `API_PROXY_TARGET` during local development and enables SPA behavior, matching the default empty `VITE_API_BASE_URL`. The service has no CORS allowlist, so a direct cross-origin API URL requires a reviewed policy covering `Authorization`, `Idempotency-Key`, and exposed replay headers; otherwise deployment must use a same-origin reverse proxy. A static host must also serve `index.html` for `/orders`, `/orders/new`, and `/orders/{id}`.

The runbook documents these requirements and warns that `dev-hung-001` is bundled client-side. This boundary is correct for the declared local demo and must not be relabeled as production-ready.

## Browser behavior is only type-checked

**Confirmed.** `npm run typecheck` passes, but `apps/web/package.json` has no test command and the web source contains no unit, integration, or browser tests. **Not tested:** valid-zero and malformed-success response boundaries, timeout followed by same-key replay, first-detail retry/backoff, malformed URL recovery, multi-tab lock fallback, direct deep links, and deployed CORS/static-host behavior.

The prior review history required tests for durable queue and polling lifecycles; the new browser implementation does not carry that coverage forward. These are the paths where the confirmed regressions occurred, so a type check is not meaningful release evidence for this behavior.
